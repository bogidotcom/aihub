# Ответ THERM теперь транзакция, а не строка в базе данных

Когда THERM только запустился, механика была простой: отправляешь $THERM в казну с вопросом в memo, и сторож превращает это в подписанную задачу на вычисление. Ответ появлялся в ленте. Чисто, но однонаправленно — единственным доказательством того, что деньги купили ответ, была веб-страница.

Это изменилось. Теперь ответ приходит так же, как пришёл запрос: on-chain.

## Как это работает

Когда задача завершена, отдельный кошелёк для ответов — никогда не казна, где лежит реальный баланс THERM — присылает вашему кошельку квитанцию: 0,000000001 $THERM, одну минимальную единицу, с ответом ИИ, записанным в memo этого перевода. Это обычный `transferChecked`, та же инструкция, что и платёж, который всё запустил, только в обратную сторону.

Разделение по кошелькам — осознанное решение. Казна остаётся только на приём; её ключ никогда не касался этого сервера и не касается сейчас. Кошелёк для ответов — отдельный, одноразовый горячий ключ, по той же схеме, что уже используется для кошелька, оплачивающего задачи на вычисление, — пополненный небольшим количеством SOL и $THERM, не больше. Если сервер когда-нибудь взломают, под ударом окажется только это пополнение, а не накопленный баланс казны.

SQLite по-прежнему хранит копию каждого вопроса и ответа — для ленты и как резервную копию — с ограничением в 500 байт на входе и 8000 символов на выходе, тем же пределом, который memo транзакции всё равно бы наложил. Но это больше не основной способ доставки ответа. Теперь это цепочка.

## Зачем отправлять транзакцию, а не просто сохранять строку?

Потому что строка в базе имеет смысл только для этого сервера. Транзакция имеет смысл для любого, кто смотрит в сеть. Любая программа на Solana, любой индексатор, любой кошелёк может прочитать ответ прямо из поля memo — без аккаунта, без API-ключа, без запроса к нам вообще. `GET /api/x402/data/:signature` по-прежнему работает для опроса вне сети, но это больше не единственный способ получить ответ.

## Это один конвейер, а не три

У THERM три способа задать вопрос — обычный перевод с memo, `POST /api/therm/pay` (собственный кошелёк сайта) и `POST /api/x402/infer` (эндпоинт Solana x402 для оплаты между программами). Все три сводятся к одной и той же строке в одной и той же таблице, и теперь все три получают один и тот же ответ on-chain, когда задача готова. Заплатите через x402 из скрипта, который ничего не знает о сайте, — и получите ответ так же, как человек, постящий из ленты: on-chain, memo на memo.

## Теперь есть и четвёртый способ, и это вообще не HTTP-маршрут

`POST /api/mcp` — это сервер Model Context Protocol: та же логика запроса цены, оплаты и чтения ответа, что описана выше, но в виде четырёх инструментов (`therm_status`, `therm_quote`, `therm_pay`, `therm_result`), которые может вызвать любой ИИ, говорящий на MCP, без SDK и без API-ключа. Агент, у которого уже есть кошелёк Solana с балансом, добавляет `iamai.kg/thermopolium/api/mcp` как удалённый сервер — и может сам запросить цену, подписать и отправить оплату, а затем опросить статус. Тот же самый танец `transferChecked` плюс memo, что описан выше, только через вызовы инструментов вместо вручную собранных HTTP-запросов. Это тот же самый код, что стоит за `/api/x402/infer`: цена из одного источника никогда не разойдётся с ценой из другого, потому что под ними одна и та же функция.

## К чему это всё на самом деле ведёт

x402 сделал оплату за вычисления чем-то, что программа может сделать без участия человека. Ответ on-chain сделал этот ответ чем-то, что программа может получить тоже без человека — ни вебхука, ни цикла опроса, просто следи за кошельком. MCP — последний кусок: теперь ИИ-агенту даже не нужно знать, что такое x402 или перевод с memo, чтобы всем этим пользоваться — он просто видит четыре инструмента, вызывает их и получает ответ, а транзакция Solana в любом случае служит квитанцией. Это и есть разница между «API с оплатой в крипте» и чем-то, во что любой ИИ, человек или программа на Solana может встроиться напрямую, вплоть до данных инструкций.
